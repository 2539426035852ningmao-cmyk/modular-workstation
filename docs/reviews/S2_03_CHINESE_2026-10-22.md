# S2-03 中文优先补充

用户明确要求 继续 优先保证中文正常 在原 #34 / PR #35 中处理 不另开并行主任务

## 发现与修订

旧实现已阻止组合输入误导航 但同时 preventDefault 取消了组合 Enter 的默认处理
新增回归实际得到 dispatchEvent=false 先记录失败 再仅移除组合 Enter 的默认取消 保留组合状态 原生 isComposing 和 keyCode 229 三种识别 Escape 关闭防护和普通 Enter 行为
没有更换语言框架或引入依赖 没有增加主进程权限 不改用户系统语言设置

## 调查依据和限制

按本机证据与用户反馈优先 再查用户讨论 社区和 GitHub 最后核对 API 说明
近期公开反馈作为线索 不直接作平台结论
[React Spectrum 原始问题](https://github.com/adobe/react-spectrum/issues/10249) 记录 CJK 组合期间 Enter/Escape 被业务处理导致输入受损
[keydown API](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event) 解释组合事件与 229 兼容判断
[dialog cancel API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/cancel_event) 提供面板取消行为背景
本项目缺陷结论来自实际默认取消断言 而非照抄外部项目修复 不能据此推断所有 Windows 输入法都曾失败或现已全部验证

## 实际验证范围

- 中文设置 工作区 空间 外观关键词及全角空白匹配
- 组合期间 Enter 默认行为保留 不导航 原文本保持
- 组合状态 ref isComposing 和 229 路径均覆盖
- Chromium CDP Input.imeSetComposition 输入设置 再 Input.insertText 提交设置 引擎事件与受控输入交互真实执行
- 组合确认不会执行命令 结束组合后的独立 Enter 才导航
- 中文深浅主题截图 html zh-CN 标签和可见替换字符检查
- 实际包验证增加专门的包内中文组合检查

本机检查全部后台执行 不显示系统输入法候选窗 不抢焦点
引擎组合测试不是原生 Windows 候选窗自动化 不能替代用户最后的中文体验验收
本轮测试 包验证 独立复核和云端结果分别留证 未执行或失败不得写通过
