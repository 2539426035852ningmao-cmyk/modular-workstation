## 1. 用户已明确确认的 13 项决策（Accepted at product level）

以下 13 项均由用户明确选择**方案 B**；这是**产品行为级确认**，不是每一个细节、技术栈或版本交付的批准。

| # | 主题 | 用户确认的决定 | 工程注意点 |
| --- | --- | --- | --- |
| D01 | 插件 UI 边界 | **统一工作站 Shell；插件内容区自由设计**，遵守标准容器、主题及系统交互规范 | 插件通过 SDK 声明入口、命令和面板；不能未经授权修改全局导航或接管其他插件 |
| D02 | 跨插件显示 | **多标签 + 受约束分屏**，底层预留高级停靠扩展 | 先支持受控布局，不将任意浮动窗口/无限停靠当作首版已批准能力 |
| D03 | 布局持久化 | **各工作空间独立记忆布局**，支持布局预设与恢复默认 | 保存布局不等于保存业务数据；恢复默认不得删除文档 |
| D04 | 正常会话恢复 | **恢复布局与上次标签，插件按需加载**；高风险任务不自动执行 | 恢复标签≠重新启动所有后台任务；不默默重复付费或破坏性操作 |
| D05 | 异常退出恢复 | **正常启动自动恢复；异常启动提供「恢复工作区」与「安全启动」** | 安全启动限制第三方插件自动激活；保留数据，避免故障循环 |
| D06 | 未保存保护 | **主程序统一协调未保存状态、退出提醒与关闭流程；插件负责实际保存和草稿恢复** | 保存失败/无响应应阻止普通关闭；不得声称可自动恢复所有未保存内容 |
| D07 | 插件故障隔离 | **单插件故障尽可能不影响 Shell 与其他插件**；保留故障标签和恢复入口 | 故障隔离≠安全沙盒；不自动重新执行危险/付费操作 |
| D08 | 插件资源管理 | **主程序统一资源监控、异常提醒、用户控制**；正常高负载创作不被无理限制 | 支持的暂停/取消/强制结束须区分；指标归属应真实可靠 |
| D09 | 统一任务中心 | **主程序统一展示/协调任务；插件负责执行与结果保存，通过 SDK 上报进度并响应操作** | 无法精确计量时不伪造百分比；取消须等待执行方确认 |
| D10 | 退出与后台任务 | **存在任务时先提醒**；用户可选择托盘后台继续、返回工作站、结束任务并退出 | 仅实际支持的任务可后台继续；后台驻留≠Windows 关机后继续 |
| D11 | 中断任务恢复 | **保留任务记录；插件支持时由用户手动继续**；不得自动重复危险或付费操作 | 云端任务先查询原任务 ID/状态，避免重复提交；记录≠一定能续传 |
| D12 | 跨插件数据交换 | **Shell 提供统一资源引用与交换协议并协调权限；插件负责处理** | 默认只授予所需资源及操作；支持原位引用和受管理副本，不强制复制所有文件 |
| D13 | 资源权限生命周期 | **最小范围、默认当前任务/流程有效；用户可主动授予并撤销持续权限** | 按插件、资源、操作和期限授权；撤销阻止后续访问但不能追回已发送数据 |

### 跨决策共同硬边界

1. **数据保护优先**：移除资源引用≠删除原文件；重置布局、插件崩溃、安全模式和会话恢复不得直接清空用户项目、素材、业务数据或草稿。
2. **高风险行为明确控制**：AI 付费请求、文件覆盖/删除、高权限调用、批量任务、危险重试，不因重启、恢复、后台运行或插件间传递而自动重复。
3. **权限必须可执行**：统一资源标识只是抽象，必须由资源解析/访问服务实际检查；不因一款插件获授权而允许它向其他插件无限转授；官方插件同样遵守最小权限。
4. **展示与能力相符**：不伪造已保存、已取消、百分比、后台可运行、可以续传或已经隔离等状态。
5. **故障边界与运行权限分离**：独立进程不能自动证明安全沙盒；应实测插件故障、IPC、文件系统和权限绕过风险。

## 2. 尚未最终定案：不要当作批准需求

- **跨插件自动协作**（仅手动、用户明确启用自动流程、插件自由事件订阅）上轮虽给出推荐方案，**用户尚未选 A/B/C**；因此不得把“自动工作流编辑器”“定时自动执行”写成已批准的首版功能。现有 `docs/ROADMAP.md` 已把跨插件工作流列于长期 S6；本次不改变它。
- **布局具体限制**（例如最多两个主编辑区、面板最小宽度、布局存储字段、跨显示器迁移）属于待原型测试的候选值。
- **资源权限能力令牌、IPC 协议、进程隔离、CPU/GPU 计量准确度、草稿恢复深度、任务历史保留期限**等细节需要正式技术设计与威胁建模。
- **Electron/Tauri 正式选型、具体设计 Token、Lobe UI 或其他 UI 库、插件宿主技术实现、高保真视觉与性能预算**尚需比较、实测与用户批准。
- **系统层面无法保证的事**：进程被强杀时可靠保存；撤销已读出/上传的数据；本地关机后继续执行本地任务；远程请求“取消”后云端一定停止且不会收费。

## 3. 给 Codex 的分阶段实施映射（不是立刻开工清单）

**S1 设计/验证**：形成 Shell 与插件 UI 边界、分屏/会话模型、退出安全流、错误/任务中心状态规范及技术可行性对照；输出高保真稿与必要 ADR。不得仅凭此交接就大范围重构现有前端。

**S2 Shell**：在获批对应 Issue 后逐步实现多标签、受约束分屏、工作空间布局持久化、基础会话/关闭安全流程和统一任务入口骨架；如功能依赖插件 SDK，用真实声明/空态，不伪造插件执行。

**S3 SDK/隔离**：依正式任务分批落地插件声明、生命周期、权限与资源访问、故障隔离、任务上报、保存协商、资源交换；每项均有权限和故障注入测试，避免一次性设计完美大框架。

**S4 官方素材插件**：用真实文件验证原位关联 vs 托管副本、删除引用 vs 删除源文件、跨插件只读传递与生成新结果登记。

**S5/S6 后续**：按真实排期完善 Windows 托盘、可靠异常恢复、后台运行、断点续传、生态兼容与可视化工作流。用户确认方向**不代表这些功能已安排在同一个版本**。
